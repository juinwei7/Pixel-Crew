# Provider Activity and Approval SDD

- Status: Accepted for implementation
- Date: 2026-07-15
- Scope: Local-first Claude Code and Codex workers

## Problem

Pixel Crew previously treated Claude Code's stream JSON as the canonical event model. Codex was adapted through `codex exec --json`, which omitted interactive approval handling and whose richer event types did not map cleanly to the UI. Tool output was also rendered only after completion, so users could not inspect a running command or subagent.

## Decisions

1. Pixel Crew owns a provider-neutral activity protocol. Provider payloads are normalized at the server boundary.
2. Codex uses its long-lived app-server JSON-RPC interface, which exposes streamed items and bidirectional approvals.
3. Claude Code keeps its persistent stream-json session and delegates permission prompts to a private local MCP bridge.
4. Approval requests are ephemeral and bound to one worker, one provider callback, and one random opaque approval id. They are never replayed after the provider process exits.
5. Sanitized approval decisions are recorded in task history, but bridge credentials and raw provider callbacks are never persisted or sent to the browser.

## Event contract

The shared runner stream adds:

- `tool_call_output_delta`: incremental stdout/stderr or tool progress;
- `approval_requested`: command/tool, cwd, reason, category, and supported decisions;
- `approval_resolved`: terminal decision for the matching request.

Provider plan progress is normalized into the visible activity/thinking stream; it is not exposed as hidden chain-of-thought.

Existing `tool_call_start` and `tool_call_result` remain for snapshot compatibility. Output deltas are compacted into the matching tool item. Unknown provider items are ignored without terminating a turn.

## Approval lifecycle

1. The provider pauses and sends a request to its adapter.
2. The adapter registers an opaque request and emits `approval_requested`.
3. The UI displays the exact sanitized action and offers allow once, allow for session when supported, or deny.
4. `POST /api/workers/:workerId/approvals/:approvalId` resolves the live callback exactly once.
5. The adapter replies through Codex JSON-RPC or the Claude permission MCP tool. Execution continues in the same turn.
6. Interrupt, provider exit, worker deletion, or server shutdown cancels every pending request.

## Security

- The public approval endpoint remains loopback-origin restricted.
- Approval ids are random and checked against the worker id.
- Claude bridge requests require a per-process bearer secret and originate on loopback only.
- The browser never supplies provider-native payloads; it selects from decisions generated by the server.
- No global or permanent approval rule is written in the first version.
- Command, cwd, reason, and tool input are length-bounded before broadcast or persistence.

## UI

- INPUT is available as soon as an activity starts.
- Incremental OUTPUT is visible while an activity is running.
- An approval card is expanded and visually distinct from completed tool rows.
- A worker waiting for approval remains busy but shows `等待核准` instead of failure.
- Completion shows exit status, duration, and bounded aggregated output.

## Compatibility

- Existing stored events replay unchanged.
- Existing Codex thread ids are resumed through app-server when possible; an invalid legacy id starts a clean thread while preserving the Worker.
- If app-server or Claude's permission prompt option is unavailable, the provider reports a clear capability error instead of presenting a non-functional approval button.

## Acceptance criteria

1. A running Codex command shows its input and output deltas before completion.
2. Codex command and file-change approvals can be accepted once, accepted for the session, or denied without restarting the turn.
3. Claude permission prompts can be accepted or denied through the same UI.
4. Reconnecting the browser restores live pending approval cards while the provider callback exists.
5. Interrupting or deleting a worker cancels pending approvals.
6. Provider parser, reducer, API, reconnect, and safety tests pass.
