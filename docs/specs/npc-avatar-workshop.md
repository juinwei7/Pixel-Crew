# NPC Avatar Workshop SDD

- Status: Accepted for implementation
- Date: 2026-07-15
- Scope: Local-first MVP

## 1. Problem

Pixel Crew currently assigns every Worker one of the built-in color variants. Users need a simple way to make a Worker recognizable without preparing a complete animation sheet or learning PixiJS asset rules.

The application is local-first, so source images and generated avatars must remain on the user's machine. Imported files must not become repository assets or be committed accidentally.

## 2. Goals

1. Let a user customize an existing Worker from the interface.
2. Accept PNG, JPEG, WebP, and animated GIF source images in the browser.
3. Crop, remove a simple flat background, reduce the palette, and normalize the result to a transparent 24 × 32 PNG.
4. Preview the exact pixels before saving.
5. Store only the normalized PNG, or the validated original GIF, locally and persist an `avatarId` on the Worker.
6. Update the office character immediately without creating a new Worker or conversation.
7. Let the user restore the built-in appearance.

## 3. Non-goals

- Inferring anatomically correct side, back, work, and walk frames from one image.
- AI image generation or uploading source images to a remote service.
- SVG, video, or arbitrary sprite-sheet import.
- Sharing an avatar library between machines.

A full sprite-sheet editor is a possible phase-two feature. The MVP uses the same normalized image for every state and adds small movement, flip, and bounce effects in PixiJS.

## 4. User experience

The Worker list exposes a small appearance action. It opens an **Avatar Workshop** modal for that Worker.

The modal contains:

- a local file picker;
- a large pixel-perfect preview;
- zoom and horizontal/vertical position controls;
- background mode (`keep` or `remove corner color`);
- palette size (8, 12, or 16 colors);
- save, restore default, and cancel actions.

Animated GIF uses a separate path: the preview and frames are preserved, crop/palette controls are disabled, and Pixi scales the animation into the same 12 × 16 world-space footprint as other NPCs.

Saving changes the selected Worker in place. Changing provider, workspace, or avatar must never create a new Worker when the Worker has no conversation history.

## 5. Processing pipeline

All source processing happens in the browser:

1. Validate MIME type, file size (maximum 5 MiB), and decoded dimensions (maximum 4096 × 4096).
2. Decode the image with `createImageBitmap`.
3. Fit it into a 24 × 32 canvas using nearest-neighbor sampling, user zoom, and offsets.
4. Optionally make pixels close to the four-corner background color transparent.
5. Reduce opaque pixels to the selected palette size with a deterministic color quantizer.
6. Export the 24 × 32 canvas as PNG.

Only this normalized PNG is sent to the local Pixel Crew server for static sources. GIF cannot be safely re-encoded frame-by-frame with the browser canvas, so the original GIF is stored locally with a 2 MiB / 320 × 320 / 120-frame limit. Its logical canvas multiplied by its frame count may not exceed 8,000,000 decoded pixels. It is served back with `image/gif` plus `nosniff`.

## 6. Persistence and API

`workers` gains a nullable `avatar_id` column. The public Worker state gains `avatarId: string | null`.

Normalized files are stored in:

```text
server/data/avatars/<random-id>.png
```

`server/data/` is already ignored by Git. `AVATAR_DIR` may override the location for testing or packaging.

Endpoints:

- `PUT /api/workers/:id/avatar` with `{ "dataBase64": "...", "mimeType": "image/png|image/gif" }`
- `DELETE /api/workers/:id/avatar`
- `GET /api/avatars/:avatarId`

The server accepts either a valid PNG whose IHDR dimensions are exactly 24 × 32 and whose decoded size is at most 32 KiB, or a structurally valid GIF within the byte, dimension, frame, and decoded-pixel limits above. Filenames and extensions are generated by the server and never derived from user input. Replaced or deleted avatars are removed when no Worker references them. Avatar replacement is persisted before the previous file is removed; a database write failure restores the prior selection and removes the unreferenced new file.

## 7. Rendering

`Person` retains the built-in textures and can additionally load one custom texture. When present, the custom texture is used for all visual states:

- horizontal movement mirrors the texture;
- walking adds a subtle one-pixel bob;
- working adds a slow bob;
- celebration adds the existing jump motion.
- GIF files are decoded into timed frames through PixiJS `GifSource` and played by `GifSprite`; the GIF's own frame delays are preserved, with 20 FPS used only when delay metadata is missing.

Loading is asynchronous and guarded so a stale request cannot overwrite a newer avatar selection.

## 8. Failure handling

- Invalid source files show a specific message in the modal.
- Invalid or oversized normalized PNG data returns HTTP 400.
- Unknown Workers or avatars return HTTP 404.
- A failed save keeps the prior avatar and leaves the editor open.
- A failed custom texture load falls back to the built-in character and reports the decoding error in the UI.
- Replacing or removing a GIF destroys its `GifSprite`, stops ticker updates, and unloads its Pixi asset cache entry.

## 9. Acceptance criteria

1. Uploading a valid PNG/JPEG/WebP shows a 24 × 32 pixel-perfect preview.
2. Crop, background, and palette controls update the preview without a server request.
3. Saving updates the same Worker and survives a server restart.
4. Restoring default removes the custom appearance and persists the change.
5. Static original source files are not written to disk; GIF is persisted only after explicit save and within documented limits.
6. Stored avatar files are ignored by Git and are never addressable through path traversal.
7. Existing Workers without `avatar_id` continue to load normally.
8. Store, image-processing, API, and frontend tests pass; production builds succeed.
